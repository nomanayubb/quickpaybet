## 1. What this project is (in plain terms)

**QuickPayBet** is a sports betting website being built for a client. The client (communicating mostly in Urdu/English mixed, see `docs/goal.txt` for the original brief verbatim) asked for:

- A working betting site with **accurate odds math**, not a toy.
- Full **admin panels**, extensible later (e.g. adjustable per-user/per-master bet limits, ability to turn affiliate payouts on/off, control who can withdraw as a "master" account or not).
- A **fully automatic workflow**: real-time odds come in → user places a bet → when the match finishes, the system automatically checks the result → automatically credits or debits the user's balance → automatically verifies crypto payments — with **no manual work** required day-to-day.
- Odds should come from a real provider by default, but **admin must be able to override/adjust them** manually from the admin panel (e.g. add or reduce margin).
- **Crypto payments** first, but built so other payment methods/countries can be added later without a rewrite.
- Everything **highly modular and flexible** — new features (casino games, new payment providers, new odds sources) must be addable later without breaking what exists.
- **Strong security** around odds/rates so nothing can be hacked, cheated, or bypassed.
- Budget-conscious: free/cheap technology choices only.
- The client explicitly told the AI coder to **proceed and complete tasks without stopping to ask permission each time**, to save on token/API costs.

## 4. Every Django app: purpose and files

### 4.1 `apps/accounts` — users, roles, auth
Custom `User` model (extends `AbstractUser`): `email` (unique, login field), `role` (`user`/`agent`/`master`/`admin`), `parent` (self-FK — builds the affiliate hierarchy), `commission_rate`, `min_bet_amount`, `max_bet_amount`, `is_betting_enabled`. `PasswordResetToken` model. JWT register/login/refresh, "me" endpoint, password reset (email-based), admin endpoint to edit a user's role/limits/commission — **this last endpoint had a privilege-escalation hole, fixed this session; see Section 8.**

### 4.2 `apps/wallet` — balances and transaction ledger
`Wallet` (balance, reserved_balance) and `WalletTransaction` (ledger row). `services.py` has `deposit_funds()`/`withdraw_funds()` — the only functions allowed to change a balance, both atomic with row locking. This core money arithmetic is solid and was not part of the problems found. A `Wallet` is auto-created via signal when a `User` is created.

### 4.3 `apps/sports` — sports, tournaments, matches, odds pipeline
`Sport`/`Tournament`/`Match` models. `providers.py` is the odds-provider adapter: `BaseOddsProvider` interface, `MockOddsProvider` (default), `TheyOddsAPIProvider` (real integration with The Odds API). `pricing.py` applies house margin and handles two-outcome (no-draw) markets. Management commands: `sync_sports`, `sync_odds` (pulls matches/odds, supports `--sport`/`--margin`), `sync_results` (pulls finished scores, settles bets, supports `--sport`). A Celery task auto-flips `Match.status` to `LIVE` once `start_time` passes.

### 4.4 `apps/bets` — the betting engine
`Bet` (single), `ParlayBet` + `ParlayLeg` (multi-selection). All business logic lives in `services.py`, not views: `place_bet()`, `place_parlay_bet()`, `settle_bet()`/`settle_bets_for_match()`, `refund_bet()`, parlay settlement helpers, and affiliate commission crediting on losing bets. Money math here is correct and atomic.

### 4.5 `apps/payments` — crypto deposits/withdrawals
`CryptoPayment` model. `providers.py`: `BasePaymentProvider` interface, `MockPaymentProvider` (default), `NOWPaymentsProvider` (real API calls + HMAC webhook verification, plus `authenticate()`/`verify_payout()` for the manual admin payout flow). `services.py` creates a pending `CryptoPayment` and, on a **provider-verified webhook**, credits the wallet; `create_withdrawal_request()` (the automatic path used by the API/web withdraw forms) deducts+ledgers atomically, calls the provider, and auto-refunds if the provider rejects the payout — money can never be silently lost or fake-credited; `initiate_manual_payout()`/`confirm_manual_payout()` (the admin-driven path, see `apps/web/views.py:admin_withdrawal_process_view` and `/panel/withdrawals/`) handle the real NOWPayments 2FA-per-batch flow. **Withdrawals did not actually call the provider at all before this session — fixed; see Section 8.**

**Live-tested against the real NOWPayments account (2026-09-06):** deposit creation works end-to-end (confirmed: a real deposit address was generated). The IPN secret was also provided and tested — and testing it caught a real bug: `verify_webhook()` was hashing the raw request body directly, but NOWPayments actually signs the JSON **re-serialized with recursively sorted keys** (`json.dumps(data, separators=(',', ':'), sort_keys=True)`) before hashing. The old code would have silently rejected essentially every real webhook, meaning deposits would never have auto-confirmed once a real provider went live. Fixed and confirmed correct with a realistic simulated webhook (accepts a correctly-signed payload, rejects a tampered one).

**Payouts — a manual admin tool, not full automation, and that's intentional.** NOWPayments requires a 2FA code to release *every single payout batch* — this is confirmed from reading their own official SDK source (`NowPaymentsIO/nowpayments-sdk-nodejs` on GitHub), not guessed. That means real, hands-off, zero-touch automatic withdrawals are not something NOWPayments allows at all, for anyone — a human has to be in the loop for every payout, by their design. Building around that would mean defeating the exact security control that protects the client's funds, which this project won't do.

What was built instead: `/panel/withdrawals/` (admin-only) lists pending withdrawal requests; "Process" walks an admin through (1) NOWPayments email+password entered directly into that page — sent straight from the admin's browser to this server to this server's call to NOWPayments' `/v1/auth`, never stored, never logged, never seen by an AI assistant — which creates the payout batch, then (2) the 2FA code from an authenticator app to confirm it via `/v1/payout/<batch_id>/verify`. The exact request/response shapes for `/v1/auth`, `/v1/payout`, and the verify endpoint were confirmed by reading NOWPayments' own official SDK source code on GitHub (not guessed, not scraped from a JS-rendered docs page that wouldn't load) — `authenticate()` was live-tested against the real API with intentionally wrong credentials and got back NOWPayments' real "Incorrect login or password" error, confirming the request format is correctly understood by their server. **The full flow has not yet been tested with a real password + real 2FA code** — that step can only be done by the client themselves, ideally with a small test amount first (tracked in `client tasks.md`).

The fully-automatic withdrawal path (`create_withdrawal_request`, used by the wallet API/web withdraw forms) still correctly and safely fails without a JWT and auto-refunds the user — that's expected, not a bug: those paths never have a password to work with, by design.

### 4.11 `apps/exchange` — Betfair-style back/lay betting exchange (added 2026-09-07)
A second, completely separate betting mode alongside the fixed-odds sportsbook in `apps/bets`: instead of betting against the house at admin-set odds, users bet *against each other* by placing **back** (for) or **lay** (against) orders at odds *they choose*, and the platform matches compatible orders together (a real limit order book, price-time priority — not a simplified "house is the counterparty" shortcut).

- `models.py` — `ExchangeConfig` (singleton row, admin-editable commission % on winnings, default 5%, via `ExchangeConfig.get_solo()`); `ExchangeOrder` (`user`, `match`, `selection` home/draw/away, `side` back/lay, `odds`, `stake`, `matched_stake`, `status`); `ExchangeFill` (one matching event between exactly one back order and one lay order — `odds` here is always the *resting* order's price, `commission_amount` recorded for audit).
- `services.py` — `place_order()` (validates, reserves exposure, then matches against the book — **back** exposure = stake; **lay** exposure = `stake*(odds-1)`, its liability if the backed outcome happens; reuses the previously-unused `Wallet.reserved_balance`/`available_balance` fields, no wallet schema change needed); `cancel_order()` (releases only the unmatched remainder — already-matched fills stand); `settle_exchange_for_match()` (mirrors `apps.bets.services.settle_bets_for_match()`, called from the exact same call sites — `sync_results`, the admin settle/cancel actions in both `apps/sports/admin.py` and `apps/web/views.py`, and the Celery settlement task — so it runs automatically with zero new scheduling); `get_order_book()` (aggregated prices for display).
- **A subtle but important design point, worth remembering if this code is ever touched again:** exposure reserved/released always uses each order's *own* requested odds, while actual profit/loss paid between the two matched users always uses the *fill's* execution odds (which can be a better price than either side originally asked for — "price improvement"). Mixing these up would either leave `reserved_balance` slowly drifting wrong over time, or shortchange/overcharge one side of a fill that got matched at an improved price. Verified explicitly with a dedicated test (`test_price_improvement_backer_gets_better_price`) and with exact-number settlement assertions, not just "it ran without crashing."
- Self-matching (a user's own resting order matching their own new order) is deliberately excluded in the matching query.
- **Web UI**: an "Exchange" section on the match detail page (order book, place-order form, cancel your own open orders), a new "My Exchange Bets" page, and "Exposure" surfaced on the wallet page.
- **Admin dashboard** (`/panel/exchange/`, added 2026-09-07, Phase 2a): a read-only overview page — summary stat cards (commission earned all-time and last 7 days, currently open orders, total exposure locked system-wide via `Sum(Wallet.reserved_balance)`, fills settled, total matched volume), an "Open Orders" box and a "Matched Fills" box, each independently searchable/filterable/paginated using the exact same GET-param-prefix pattern already established in `admin_user_ledger_view` (`apps/web/views.py`). Adds no new wallet mutations or settlement logic — purely queries existing data. Editing the commission rate still happens in Django's built-in `/admin/` (`apps/exchange/admin.py`), which was already there from Phase 1 and isn't duplicated here.
- **Cash-out** (`/exchange/orders/<id>/cash-out/`, added 2026-09-07, Phase 2b): lets a user lock in an estimated profit/loss on a matched position before the match ends, staying true peer-to-peer — it works by computing and placing a real opposing order (e.g. a LAY order to close a BACK position) sized to exactly offset the position's current matched stake, and running it through the exact same, unmodified `_match_order()` matching engine from Phase 1. `apps/exchange/services.py:cash_out_order()`/`preview_cash_out()`. Key formula: `target_notional = order.matched_stake + Σ(fill.stake*(fill.odds-1))` across the order's own pending fills — identical arithmetic for both back and lay orders. The book is walked best-price-first, taking full price levels and then an *exact fraction* of the final level needed to land precisely on the target — never overshooting it, since overshoot would break the equal-P&L guarantee itself (proven with concrete numbers in `apps/exchange/tests.py:ExchangeCashOutTests`, not just asserted). If the book can't fully cover the target, whatever it can absorb is cashed out (partial, Betfair-style immediate-or-cancel of the unfilled remainder) and the rest of the position stays live — the UI is explicit that a partial cash-out is *not* a single guaranteed number. The shown value is always labeled "estimated," not "guaranteed" — see rule 20. UI: a "Cash Out" button next to each matched order on the match detail page, showing a live estimate refreshed every 5s by a small `fetch()` poll (`exchange_cash_out_preview_view`, read-only); clicking always executes immediately against the real book at that moment (`exchange_cash_out_view`), regardless of what the button last displayed.
- Built behind a formal plan-and-approval step given the money-correctness stakes (on the client's own insistence — "this project is not a joke... we cannot risk website"), with 14 dedicated tests (exact-price match, price improvement, partial fills across multiple counterparties, no-match, self-match exclusion, insufficient-balance rejection, cancel behavior, and settlement math for both back-wins and lay-wins scenarios verified to the exact expected wallet number) plus live HTTP-level verification (real page loads, real form submissions, real admin settle action) before being called done. The Phase 2a dashboard was verified the same way: live test data created and settled via `manage.py shell`, then hand-checked against every stat-card number and table row through the actual running page (including confirming filters narrow results and that a non-admin gets redirected away), all test data deleted afterward.

### 4.12 `apps/cashback` — loss-cashback / rebate system (added 2026-09-07)
A genuinely new, separate balance concept (distinct from `Wallet.balance`/`reserved_balance`): when a user loses a bet — sportsbook (single or parlay) or exchange — a configurable percentage of that loss is credited back to them, optionally locked behind a wagering (turnover) requirement before it can be withdrawn. Requested by the client mid-way through the exchange cash-out work as a separate, larger feature to design afterward; three genuine requirements ambiguities (trigger timing, scope, what "wagering requirement" and "unlock" actually mean) were resolved directly with the client before any code was written — see the plan file referenced in this session's history, and rule 21 below.

- **Config** (`apps/cashback/models.py:CashbackConfig`) — global singleton (`get_solo()`, same pattern as `ExchangeConfig`): on/off, default rate %, default wagering multiplier (0 = immediately withdrawable), and a `deduct_original_on_unlock` toggle. **Per-user overrides** live as three new nullable columns directly on `apps.accounts.models.User` (`cashback_enabled_override`, `cashback_rate_override`, `cashback_wagering_multiplier_override`) — `None` means "inherit the global value," the exact same convention already used by `min_bet_amount`/`max_bet_amount`. Editable per-user from the existing Manage Users edit page; editable globally from Django's built-in `/admin/`.
- **`CashbackCredit`** (`apps/cashback/models.py`) — one row per credit event, with every rule that determined it (rate, multiplier, deduct-on-unlock) **snapshotted at creation time**. This is the concrete mechanism that satisfies the client's explicit, non-negotiable requirement that changing settings later must never retroactively corrupt an already-issued credit or a user's in-flight wagering progress.
- **Trigger (credit side)** — `apps/cashback/services.py:credit_cashback_for_loss()`, called at the exact same three loss-determination points the affiliate-commission feature already hooks (`apps/bets/services.py:settle_bet()`'s LOST branch, `_settle_parlay_if_ready()`'s LOST branch, `apps/exchange/services.py:_settle_fill()`'s loss branch) — mirrors `_credit_affiliate_commission()` exactly (self-locks the wallet, no-ops cleanly when disabled or the amount is zero).
- **Wagering progress** — `apps/cashback/services.py:record_wager()`, called at the three stake-commitment points (`place_bet()`, `place_parlay_bet()`, `apps/exchange/services.py:place_order()`, and `cash_out_order()`'s opposing leg) with the wallet already locked by the caller. Measured by total amount *staked* (turnover), regardless of win/loss on those wagers — confirmed with the client, not assumed. If a user has multiple open credits at once, each new stake counts toward *every* open requirement independently (a judgment call, not separately confirmed, flagged as such in the plan — simpler than FIFO/splitting and never less generous to the user).
- **Wallet mechanics** — new `Wallet.locked_cashback_balance` field (denormalized running total, updated exactly like `reserved_balance` already is) and a new `withdrawable_balance` property (`available_balance - locked_cashback_balance`). Locked cashback money stays fully usable for placing new bets/orders from the moment it's credited (only `withdraw_funds()` checks the new, stricter `withdrawable_balance` — `available_balance`, used for bet/order eligibility, is untouched). Unlock is a "label lifts off, nothing deducted" by default (confirmed with the client); the `deduct_original_on_unlock` toggle exists for the opposite behavior the client's original request also mentioned, defaulting off.

### 4.13 `apps/rewards` — deposit-milestone reward packages (added 2026-09-07)
A small admin-managed catalog: a user whose lifetime confirmed deposits cross a package's threshold gets that package's commission-rate bonus added to their `User.commission_rate` permanently, once per package. Requested by the client alongside the Commission History addition below; confirmed via `AskUserQuestion` before building: the trigger is a deposit milestone (not wagering or referrals), the reward is a permanent `commission_rate` boost (not a one-time wallet credit), and admin manages multiple named packages (not one global rule).

A plain user with nobody referred underneath them has a `commission_rate` that's stored and displayed but never read by any other code path — this reward is genuinely valuable to masters/agents (existing or future), inert for a solo bettor unless they also refer others. Documented up front so this is understood, not discovered later.
- **`RewardPackage`** (`apps/rewards/models.py`) — name, `deposit_threshold`, `commission_rate_bonus` (0–99, validated), `is_active` (soft-disable, same convention as `Sport.is_active` — no hard-delete anywhere in this project). **`UserRewardClaim`** — one row per user per package ever earned, `unique_together=('user','package')` enforced at the database level (not just application logic), with the bonus and the deposit total at claim time both **snapshotted** — editing a package later only affects future claims, the same "snapshot the rule" pattern as `CashbackCredit`/`ExchangeFill.commission_amount` (rule 21).

That function's own `CryptoPayment.status=PENDING` guard is what makes this safe to call exactly once per real confirmed deposit (webhook replays raise before reaching this code) — no separate idempotency mechanism needed. ### 4.14 `apps/sports` — ParlayAPI odds provider added (Phase 1 of a much larger direction, 2026-09-07)
The client described a large, multi-part future direction in one long message (`new major change 97s .txt`): swap the odds provider, build a hybrid WebSocket/polling real-time architecture, admin-configurable refresh timing, PostgreSQL storage-retention settings, an odds-margin admin tool, Excel exports, Easypaisa, disaster-recovery domain migration, and a second closed-hierarchy subdomain site with no self-signup. - **The client's plan named Betfair as the intended data source for back/lay odds via a new provider, ParlayAPI. - **`ParlayAPIProvider(BaseOddsProvider)`** (`apps/sports/providers.py`) — added *alongside* the existing `MockOddsProvider`/`TheyOddsAPIProvider`, nothing removed. Config via `PARLAY_API_KEY`/`PARLAY_API_URL`/`PARLAY_BOOKMAKER` env vars. Auth via `X-API-Key` header. - 14 new tests (mocked HTTP, no real network calls in the automated suite) covering sport-list mapping, Pinnacle-preferred-with-fallback selection, the fixed outcome-matching logic, skip-on-missing-price behavior, completed-score mapping, and the provider factory. Full suite: 81 tests.

### 4.15 Real-time odds refresh — simple polling, admin-configurable, viewer-gated (Phase 2, 2026-09-07)
The client described a WebSocket-based architecture for this in real detail. Presented as an explicit choice rather than assumed: this project has zero real-time infrastructure today (no Django Channels, no ASGI server wired into any deployment path, nginx has no WebSocket-aware proxy config, no production deployment exists yet to test any of that against) — the client chose to reuse the site's existing, already-working polling pattern (the Cash Out button already does `fetch()` + a JS timer against a small JSON endpoint) instead of building that infrastructure now. Real WebSocket push remains a valid future upgrade once there's enough real traffic to justify the added deployment complexity — nothing here forecloses it.

- **No separate background timer exists anywhere for this.** A viewer's own poll request is what triggers a refresh check — `apps/sports/realtime.py:maybe_refresh_sport_odds()` uses `cache.add(f'odds_refresh_lock:{sport.id}', True, timeout=interval)`, which is atomic and succeeds for only the first caller within a window; every other concurrent viewer's poll within that same window reads what's already in the database instead of triggering a second real fetch. Zero viewers on any match of a sport → zero poll requests → zero provider calls, automatically, with no special-casing needed. Also credit-efficient by construction, not just by discipline: ParlayAPI's odds endpoint returns a whole sport's matches per call, so one triggered refresh updates every match of that sport at once.
- **`RealtimeOddsConfig`** (`apps/sports/models.py`) — the fourth singleton in this codebase using the `get_solo()`/`pk=1` pattern (`ExchangeConfig`, `CashbackConfig`, this one), edited via Django's built-in `/admin/` like the other two global configs (not a custom `/panel/` page — this is a rarely-changed global setting, not a per-user override). Every timing field has `MinValueValidator`/`MaxValueValidator` bounds so an admin genuinely cannot enter a value that breaks anything: `is_enabled` (default off), `live_refresh_seconds` (default 20, bounds 5–120), `not_started_refresh_seconds` (default 120, bounds 30–3600), `proximity_boost_seconds`/`proximity_window_minutes` (default 60s within the last 30 minutes before kickoff), `min_viewers_for_realtime` (default 1 — a match's odds only refresh once at least this many people are actively on its page; below it, odds stay exactly where they last were), `bet_acceptance_delay_seconds` (default 5).
- **Viewer counting** (`apps/sports/realtime.py:record_viewer_heartbeat()`) uses the visitor's own Django session (`request.session.session_key`, created on first poll if one doesn't exist yet — works uniformly for logged-in and anonymous visitors) as their identity, stored as one cache entry per match (`{session_key: last_seen}`, pruned on every heartbeat) — built entirely on Django's existing cache framework (Redis in production, `locmem` locally), no new presence infrastructure.
- **A deliberate deviation from a literal reading of the request, explained rather than silently built:** the client's "5-7 second bet-acceptance delay" is normally there to stop a user exploiting odds they know are stale. Implementing it as an actual `time.sleep()` in the view would hold a Gunicorn worker thread for that whole window — this project's production config runs only **3 workers** (`Dockerfile.prod`), so even light concurrent betting activity could exhaust the worker pool and take the whole site down for the sake of one feature. Built instead as odds re-validation: the bet form now also submits the odds the user was actually shown, and `apps/bets/services.py:place_bet()` rejects the bet (clear message, nothing charged) if the match's current odds have moved by more than 2% (`BET_ODDS_TOLERANCE`) since then — the same underlying protection, without the availability risk. Verified live in both directions: a bet submitted while the page's own live poll had already caught up to a real odds change was correctly accepted at the new, current price; a genuinely stale submission (realtime polling off, odds changed after page load) was correctly rejected with a clear message and created no bet.
- **Explicitly out of scope for this phase:** "outright/futures" markets and a refresh tier for them — there is no outright/futures data pipeline anywhere in this codebase today (the sync commands only ever handle head-to-head matches), so there's nothing yet to attach a refresh tier to; a separate, later piece of work if the client wants outrights at all.
- **Coexists with, does not replace, the existing Celery Beat schedule** (`sync-odds-recurring` every 6h, `sync-results-recurring` every 30 min, `config/celery.py`) — that schedule serves a different purpose (general catalog freshness for browsing/listing, and settlement-triggering via `sync_results`), independent of whether anyone is actively watching a specific match. Once `ODDS_PROVIDER` is ever switched to `parlayapi` for real, that existing schedule will itself start consuming real credits on its own fixed cadence, separately from whatever this on-demand mechanism uses — worth remembering before that cutover, not a new cost introduced by this phase.
- 17 new tests (config validators, refresh-interval tier selection for live/not-started/proximity-boost/finished, viewer heartbeat accumulation and staleness pruning, the throttle allowing exactly one real fetch per window, and both directions of the odds re-validation) plus live verification through the real running site: the poll endpoint's `next_poll_seconds` was confirmed to change instantly after an admin config edit (no restart), the min-viewers and global-disable gates were confirmed via direct requests, and the bet re-validation's accept/reject paths were both proven with real form submissions. All test data deleted afterward, config reset to safe (disabled) defaults. Full suite: 98 tests.

### 4.16 Odds-adjustment admin tool — global default + per-match override (Phase 4, 2026-09-07)
The client's original request was "increase/decrease a match's (or all matches') odds by any number from 0.1 to 10, including for one specific user differently." The per-specific-user part was already declined (rule 22 — a targeted-player-manipulation risk, not risk management). For the rest, the client was asked to disambiguate the actual mechanic — a flat add/subtract on the odds number itself, or an adjustment to the bookmaker margin percentage the site already applies — and explicitly chose **the flat add/subtract**, the riskier of the two readings, over the safer margin-based option that was recommended.

- **`OddsAdjustmentConfig`** (`apps/sports/models.py`) — the fifth singleton in this codebase using the `get_solo()`/`pk=1` pattern, edited via Django's built-in `/admin/`: one field, `default_adjustment` (bounds **-10.00 to 10.00**, default 0.00 — the exact range the client asked for).
- **`Match.odds_adjustment`** (new nullable field, same bounds) is a per-match override, editable both from Django admin and from the existing `/panel/matches/<id>/edit/` page. `None` (blank) means "use the global default" — the same convention already used elsewhere in this project for per-record overrides of a global setting.
- **`apply_odds_adjustment()`** (`apps/sports/pricing.py`, alongside the existing `normalize_odds()`) adds the effective adjustment to each odds value and **hard-clamps the result to a floor of 1.01** — the same minimum this codebase treats as the only valid odds value everywhere else. This clamp is the actual mechanism behind the client's own stated worry ("magar mukammal database khrab na ho aesa krne se" — but the database must not get corrupted by doing this): no matter what an admin enters, a match's stored odds can never reach or drop below 1.00. Live-verified with a deliberately extreme case (a 1.20 favorite against a -10.00 adjustment) — clamped to 1.01 exactly, while a longer-priced outcome on the same match that didn't need clamping was correctly left unclamped.
- **Applied at the single point odds get written to the database** — right after `normalize_odds()` in both `apps/sports/realtime.py:maybe_refresh_sport_odds()` and `apps/sports/management/commands/sync_odds.py:_process_match()` — so the odds a user is shown, the odds they bet at, and the odds stored in the database are always the same number; there is no separate "raw" vs "adjusted" value to keep in sync anywhere.
- **An already-placed bet is never retroactively affected.** `Bet.odds`/`potential_payout` are written once at placement time and never re-read from the match afterward — confirmed by re-checking `apps/bets/services.py` and proven with a live test: a bet was placed at 2.00, the match's adjustment was then changed and its odds re-refreshed to a different value, and the already-placed bet's own recorded odds stayed exactly 2.00. Same "snapshot, don't reference" principle as cashback and exchange commission (rule 21).
- `sync_odds.py`'s `_process_match()` previously wrote matches with `update_or_create()` and never looked up an existing row first; it now does a lookup first specifically so a match's own `odds_adjustment` override survives being re-synced rather than silently being ignored on every catalog refresh.
- 10 new unit tests (zero/positive/negative adjustment, floor-clamping, `None`-draw pass-through for two-outcome markets, global-default vs. per-match-override resolution, per-match override taking precedence during a live refresh, and the already-placed-bet-is-unaffected guarantee) plus live shell verification of both write paths (`maybe_refresh_sport_odds` and the `sync_odds` command) and a real browser round-trip through the `/panel/matches/<id>/edit/` form (logged in as a throwaway staff account, filled and submitted the new field, confirmed the saved value in the database, then deleted the account and all test rows). Full suite: 111 tests.
- **Follow-up, 2026-09-08 — range widened from ±10.00 to ±99.00.** The client explicitly asked for no artificial cap on how far an admin can shift odds away from the live price. Widened across all 6 fields that shared this bound (`Match.odds_adjustment`, `OddsAdjustmentConfig.default_adjustment`, `User.odds_adjustment_override`, `UserMatchOddsOverride.adjustment`, and the two Custom Odds relative-lay-delta fields on `HouseLiquidityConfig`/`PricingOverride`, Section 4.20) — a pure validator/label change, no schema impact (`max_digits=4` already covers up to 99.99). New boundary tests added; live-verified on the real `/panel/matches/<id>/edit/` form.

### 4.18 House-seeded synthetic lay pricing for the exchange (Phase 6, 2026-09-07)
Pinnacle (Section 4.14) only ever gives one-sided bookmaker ("back") prices — no bookmaker offers a "lay" price, that's an exchange-only concept. The client wanted the site's existing peer-to-peer exchange (Section 4.11) to also show a computed lay price next to each selection, Betfair-style, genuinely bettable (real wallet deduction, exposure, settlement, history) — not cosmetic. Two decisions were confirmed directly with the client rather than assumed: (1) the site's own liability from real users backing against its computed lay price must be capped, admin-configurable, per match+selection — not open-ended, the same risk-management posture a real bookmaker/market-maker uses; (2) the back→lay spread is admin-configurable both globally and per-match, using a flat digit add/subtract — explicitly the same mechanic as the already-shipped odds-adjustment tool (Section 4.16), not a percentage margin.

- **Ships fully off by default** (`HouseLiquidityConfig.is_enabled = False`, same posture as `RealtimeOddsConfig.is_enabled`) — none of this code changes any live behavior until an admin explicitly creates a house account, funds it, and turns the switch on. No automatic activation anywhere.
- **`HouseLiquidityConfig`** (`apps/sports/models.py`) — the sixth `get_solo()` singleton in this codebase: `is_enabled`, `default_lay_spread` (bounds **0.01–5.00**, deliberately never allowed to reach zero/negative even at the admin-input layer, unlike `odds_adjustment`'s legitimate negative range — a spread must always be strictly positive, that's the whole arbitrage-safety property), `default_max_liability_per_selection`. `Match` gets two new nullable per-match overrides, same convention as `odds_adjustment`: `lay_spread_override`, `house_max_liability_override`.
- **`compute_lay_price()`** (`apps/sports/pricing.py`, beside `apply_odds_adjustment`) computes `back_odds + max(spread, LAY_SPREAD_FLOOR)` where `LAY_SPREAD_FLOOR = Decimal('0.01')` — an unconditional, code-level guarantee that a computed lay price can never equal or drop below its own back price no matter what value reaches the function, mirroring exactly how `ODDS_FLOOR` guarantees `apply_odds_adjustment` can't produce a sub-1.01 odds. The 2-way-market guarantee is structural, not a passed-through `None`: the reseeding function below simply never calls this for `'draw'` on a match with no draw market, so a draw lay price can never exist for one.
- **A real pre-existing bug was found and fixed as a prerequisite, not separately:** `apps/exchange/services.py:place_order()` validated `selection` only against the global 3-value enum, never against a specific match's actual market shape, and `get_order_book()` unconditionally built a Draw entry for every match — meaning a user could place a Draw order on a genuinely 2-way match (e.g. tennis) even though the sportsbook half of the same page already correctly hides the Draw option for one. Both functions now gate on `match.odds_draw is not None`; no template change was needed since `match_detail.html`'s exchange block is already fully data-driven off `get_order_book()`'s own returned keys.
- **The house account is a flagged `User`** (`is_house_account` boolean, `apps/accounts/models.py`), protected by a conditional `UniqueConstraint` (`condition=Q(is_house_account=True)`) so at most one can ever exist — enforced at the database level on both dev SQLite and prod PostgreSQL, and for free on the admin change form via Django's own `validate_unique()`. ### 4.20 Custom Odds: back-price freeze + 3-mode lay pricing (Phase 8, 2026-09-07)
The client wanted to (a) temporarily disable the live Pinnacle feed for a match's back price and pin it to a fixed admin-set number instead ("Custom Odds" — stays exactly at that number until changed or switched back to API), and (b) control lay independently via three modes: **API Lay** (Phase 6's existing back + house-spread behaviour), **Relative Lay** (back + a separate, newly-added admin delta, confirmed distinct from the existing house-liquidity spread), and **Custom Lay** (a fully independent fixed number). All at the same 4 scopes already established (global, per-match, per-user, per-user+match).

- **Scope boundary, decided given the constraints already established this session:** global and per-match levels feed the **real exchange order book** (`sync_house_orders_for_match`, Phase 6b); per-user and per-user+match levels can only ever change what one specific person sees/is charged on the **sportsbook** (`apps/bets`, extending Phase 7's per-user layer) — the exchange's order book is one shared, matched market, so a hidden per-user price there would be physically incoherent (a real order would still execute at the real book price), not just risky.
- **A real design flaw was caught live and fixed before shipping:** the first version stored one shared custom back/lay value per override, and live browser verification showed Home, Draw, and Away on a real match's exchange order book all displaying the identical frozen price — never a sensible market. Confirmed with the client and redesigned: `back_custom_value_home/draw/away` and `lay_custom_value_home/draw/away` are six separate fields (three each), so every selection gets its own independent custom number. `lay_relative_delta` stays a single shared field on purpose — it's added to each selection's own back, so it already produces a different lay per selection without needing to be split three ways.
- **`PricingOverride`** (`apps/sports/models.py`) — one unified table for the 3 non-global scopes (a match-only row, a user-only row, or a user+match row), rather than 3 separate models, so there's exactly one place to search/list/reset every active override, matching the client's explicit ask. Enforced via a plain `unique_together=('user','match')` plus two conditional `UniqueConstraint`s (capping the match-only and user-only kinds at one row each — `NULL != NULL` in SQL means a bare `unique_together` can't do this alone) and a `clean()` override rejecting a both-null row (the fully-global scope lives on `HouseLiquidityConfig` instead, extended with the same fields for its own scope).
- **`compute_back_and_lay()`** (`apps/sports/pricing.py`) is the one place all three lay modes and the arbitrage-safety guarantee live: after resolving back (custom replaces the raw value outright; API leaves it as the already-adjusted value) and lay (per its mode), the result is **unconditionally floor-clamped** so lay can never equal or drop below back — reusing the exact `LAY_SPREAD_FLOOR` guarantee from Phase 6, now applied to every mode's output, not just API Lay. Proven live with the client's own example: a Relative Lay delta of -1.00 on a custom back of 3.15 would naively give 2.15 (below back) — clamped to 3.16.
- **New dedicated admin panel, `/panel/pricing-overrides/`** (`apps/web/views.py`, `templates/web/admin_pricing_overrides.html`), following the existing `admin_exchange`/`admin_cashback` dashboard structure: search by user email or match teams, one row per active override with its scope and all fields, a reset (delete) action per row, and a global-default summary with its own reset link. `admin_users.html`/`admin_matches.html` each gained a small "⚠" alert flag (existence-based, same convention as every other override flag this session) linking through to the panel, so an active override is visible wherever an affected user or match is being managed, not only in the dedicated tab.
- 27 new tests across `apps/sports/tests.py` (model constraints including the both-null rejection, the match/user resolution cascade, `compute_back_and_lay` for all 3 lay modes including the per-selection redesign and the floor-clamp holding for a negative Relative delta) and `apps/exchange/tests.py` (a match-level Custom Back/Relative Lay override correctly drives the real house-seeded exchange orders, per selection). Full suite: 188 tests. Live-verified end-to-end, including the redesign: a match-level override with three different custom back values (1.95/3.50/3.80) placed through the real admin panel UI produced three real, independently-priced house exchange orders; a per-user override changed only that user's sportsbook price while the real exchange order book for the same match stayed on the match-level value throughout; deleting an override correctly fell back to the genuine live Pinnacle price.

### 4.21 Consolidated odds-refresh mode (Phase 9, 2026-09-08)
The client listed 7 things they wanted control over for "how odds must work" and explicitly asked for overlapping settings to be consolidated rather than duplicated. Of the 7, most already existed and just needed pointing out: configurable refresh timing, the "only refresh when N viewers are watching" gate, a global stop/start switch, and the bet-acceptance delay were all already built in Phase 2 (`RealtimeOddsConfig`); "use custom odds" was already Phase 8's `back_mode = custom`. Only three items were genuinely new: refreshing on schedule regardless of viewer count, stopping/starting real-time refresh for one specific match (not just the whole site), and a mode with no automatic timer at all that updates only on explicit request.

- **`RefreshMode`** (`apps/sports/models.py`) — four values: `VIEWER_GATED` (default, today's exact existing behavior), `ALWAYS` (refresh on schedule regardless of viewer count), `MANUAL_ONLY` (no automatic timer; a "🔄 Refresh Odds" button appears and forces one fetch on click), `STOPPED` (fully frozen, refuses even a manual refresh). Global scope on `RealtimeOddsConfig.default_refresh_mode`, per-match override on `Match.refresh_mode_override` — deliberately **not** a per-user scope like Phase 7/8's pricing overrides, since refresh timing is a shared, public concern everyone sees the same cadence for, not something that should differ per viewer.
- **Sits one layer above the odds-provider abstraction, by construction**: this only ever decides *when* `apps/sports/realtime.py:maybe_refresh_sport_odds()` gets called, never *how* a provider is queried — addressing the client's explicit "if we change the API in future, this must not become difficult" requirement with zero extra code, the same way every other feature built on `get_odds_provider()` already works.
- **All of it converges in one place**, `apps/web/views.py:match_odds_poll_view`: `STOPPED`/`MANUAL_ONLY` both report no timer interval, so the client JS's existing `should_continue_polling` flag naturally goes `False` and the poll loop stops itself with **zero JavaScript changes** to that mechanism; a new `?refresh=manual` query param forces exactly one fetch when in `MANUAL_ONLY` (refused outright when `STOPPED` or when the global switch is off), still governed by the existing per-sport cache-lock throttle so it can't be spammed to burn API credits; `ALWAYS` is `VIEWER_GATED`'s identical code path minus the viewer-count check.

### 4.22 Disaster-recovery encrypted database backups (Phase 10, 2026-09-08)
Item (1) of the larger client direction: a way to move the whole platform to a new domain/server if the current one gets blocked, without ever handling a plaintext password. Storage destination was confirmed with the client first: no cloud storage account exists, so backups stay encrypted on the server with an admin-panel download page rather than uploading anywhere automatically.

- **Format is Django's own `dumpdata`/`loaddata` (JSON), not a raw `pg_dump`** — a deliberate choice specifically so this could be genuinely live-tested end-to-end against the real dev database in this session (engine-agnostic; works identically whether the live DB is SQLite, as in dev, or PostgreSQL, as in Docker/CI), unlike Phase 3's PostgreSQL work which could only be confirmed by code inspection.
- **`apps/common/management/commands/backup_database.py`** — dumps every app except `contenttypes`/`auth.permission`/`admin.logentry`/`sessions.session` (these are regenerated by Django itself on `migrate` and would risk PK/FK mismatches on restore), encrypts the JSON with `Fernet` (`cryptography` package, new dependency) using the `BACKUP_ENCRYPTION_KEY` env var, writes a microsecond-timestamped `backup_YYYYMMDD_HHMMSS_ffffff.json.enc` to `BACKUP_DIR` (`backups/`, gitignored), and prunes beyond a retention count (default 14).
- **`apps/common/management/commands/restore_database.py`** — the inverse; decrypts and `loaddata`s. Refuses to run without an explicit `--confirm` flag, since it's meant for a single use on a freshly migrated, otherwise-empty database on a new server, never a live one.
- **Celery**: `apps/common/tasks.py:run_database_backup` wraps the command, scheduled nightly at 03:00 in `config/celery.py` (`nightly-database-backup`), and reused by the admin panel's manual trigger — so a manual "Trigger backup now" enqueues async work instead of blocking a Gunicorn request thread, the same 3-worker-constraint reasoning applied to the bet-acceptance delay in Phase 2.
- **New admin panel, `/panel/backups/`** (`admin_backups_view`/`admin_backup_download_view` in `apps/web/views.py`) — lists files with size/created time, "Trigger backup now", and a "Download" link that serves the already-encrypted bytes directly. Gated to `_is_full_admin` (stricter than the general `_has_dashboard_access` most `/panel/` pages use — a decrypted one of these files contains every user's password hash and every wallet balance).

## 5. Core workflow: how a bet actually settles

1. **Odds come in**: `sync_sports` (once) → `sync_odds` pulls matches/odds from the provider, applies house margin, saves `Match` rows. Scheduled via Celery Beat every 6 hours (`config/celery.py`).
2. **A match goes live automatically**: a Celery task flips `Match.status` to `LIVE` once `start_time` passes. Scheduled every minute.
3. **User places a bet**: `place_bet()`/`place_parlay_bet()` reserve the stake from the wallet and create a `Bet`/`ParlayBet` — one atomic DB transaction.
4. **Result comes in**: `sync_results` pulls finished scores, marks the match `FINISHED`, and calls `settle_bets_for_match()`. Scheduled via Celery Beat every 30 minutes — **this task was a stub that didn't actually run the command; fixed this session, see Section 8.**
5. **Settlement happens automatically**: every pending `Bet`/`ParlayLeg` is marked `WON`/`LOST`, wallets credited, and affiliate commission credited to the referrer on a loss.
6. **Everything can also be triggered manually** via Django admin actions (settle/cancel a match, edit odds/limits/commission) for admin override.

**Running the scheduler in practice:** the Beat schedule only fires if a `celery beat` process is actually running alongside a `celery worker` process. Neither `docker-compose.yml` nor `docker-compose.prod.yml` currently run a beat/worker service — only `backend` (the Django web process) is defined. This is a real remaining gap; see Section 8.

### Additional hardening (2026-09-06, same day, after the foundation pass)
- **API login had no brute-force protection** — only the web login did (a 5-attempts/60s lockout). The API login (`/api/auth/login/`) was only covered by the generic 100/hour anonymous rate, which is far too loose for password guessing. Added a dedicated `auth` throttle scope (10/hour) applied to API login, registration, and password-reset-request; confirmed live (10 attempts allowed, then HTTP 429). Also added a per-IP rate limit to the web registration and password-reset-request views, which had none at all before.
- **Withdrawal API had no dedicated rate limit** — added a `withdraw` throttle scope (10/hour) as defense-in-depth against a compromised session spamming withdrawal requests.
- **Odds override endpoint accepted negative or zero odds with no validation at all** — confirmed live: an admin/master could set `odds_home` to `-5.00` or `0` via `PATCH /api/matches/<id>/update-odds/`, which would corrupt settlement math (a bet against zero odds pays out zero; negative odds are nonsensical). Fixed in both the API (`MatchOddsUpdateSerializer`) and the web admin match forms (`apps/web/views.py`) — decimal odds must now be greater than 1.00 everywhere they can be set by a human. (Provider-synced odds via `sync_odds`/`pricing.normalize_odds()` were already safe by construction — this only affected manual overrides.)
- **CORS reviewed, not changed**: `CORS_ALLOW_ALL_ORIGINS=True` is permissive but lower-risk than it looks — `CORS_ALLOW_CREDENTIALS` is not set (defaults to `False`), so cross-origin requests can't carry cookies/session auth; JWT bearer tokens aren't automatically attached by a browser to a request a malicious site initiates. Tightening this to a specific allowed origin is still worth doing before public launch, but is genuinely blocked on the client's domain/frontend decision (`client tasks.md`) — there's no real origin to restrict it to yet.
- **Parlay bet decimal overflow.** `ParlayBet.total_odds` is `DecimalField(max_digits=10, decimal_places=2)` (max ~100 million), but nothing capped how many selections a parlay could have or how large the multiplied combined odds could get. Reproduced: a 30-leg parlay at 2.00 odds each computes a combined odds value in the billions — SQLite silently stored the wrong, truncated-precision value instead of erroring; PostgreSQL (the real production database) would hard-crash with a numeric overflow error. Fixed in `apps/bets/services.py:place_parlay_bet()` with both a sane leg cap (12) and a hard ceiling check on the computed combined odds, checked before anything is saved. Confirmed: the bad case is now rejected with a clear message, normal parlays (verified with 5 legs) are unaffected.

## 11. Rules for any AI or developer continuing this project

1. **Read this file first**, not the raw chat history.
2. **Verify by running the code, not just reading it.** This project's own history (Phase E vs. Phase F above) is the proof that reading code and git history can produce a confident, well-organized, and still-wrong picture of what actually works. Run the tests. Try the actual user flow. Reproduce a bug before believing it exists, and reproduce a fix before believing it works.
3. **Keep this file updated**, but at the level of "what's the current position and what's the goal," not a line-by-line changelog. Commit messages and git history are where the mechanical detail belongs.
4. **Business logic belongs in each app's `services.py`, never in views.**
5. **Every wallet-changing operation must be an atomic DB transaction with row locking** — money correctness is the client's top priority.
6. **Keep the provider adapter pattern** for odds and payments — new providers are new classes implementing the existing interface, never hard-coded into business logic.
7. **Never commit real secrets** into any file other than the gitignored `.env`. This has already happened once (Section 6) — don't repeat it.
8. **Never leave a development/testing shortcut reachable by real users.** The self-funding exploit fixed this session started life as exactly that. If you need a dev convenience, gate it behind `settings.DEBUG` or an explicit admin-only, audit-logged action — never a plain user-facing endpoint.
9. **The client wants large, complete units of work** delivered without stopping to ask permission mid-task — use good judgment, but bias toward finishing a full, coherent, *verified* feature rather than a half-step.
10. **Don't silently invent requirements.** Where something is genuinely undecided, it belongs in `client tasks.md`.
11. **Never commit to git unless explicitly asked to**, even when asked to "fix everything" — fixing code and committing it are different permissions.
12. **Never put a custom URL under the `admin/` prefix.** Django's built-in admin claims that whole prefix with a catch-all view; anything else routed under it is silently unreachable. The custom admin section lives at `/panel/...` for exactly this reason (Section 4.9) — keep it there.
13. **Reading code and passing unit tests are not the same as the feature working.** This project's history includes a fully-implemented, unit-tested-adjacent admin section that was completely unreachable in the browser the whole time, and a codebase that "looked done" while having a live self-funding exploit. When in doubt about whether something really works, click through it as a user would, or reproduce it with a script that hits the real URL — don't stop at reading the source.
14. **`Model.objects.create()` does not run field validators.** Only `full_clean()`, a `ModelForm`, or a DRF serializer does. Several real bugs in this project (an unvalidated `Sport.slug`, unvalidated `Match` odds, an unbounded `ParlayBet.total_odds` overflow) all came from code creating a model instance directly and assuming the field definition itself was protection. It isn't — validate explicitly wherever a model is created directly from user input.
15. **Never store recoverable/plaintext passwords, no matter who asks or why.** This was explicitly requested once (to relay forgotten passwords via WhatsApp) and declined — the risk isn't about who's allowed to see it in the admin UI, it's that the data exists in recoverable form at all, which turns any future breach, stolen backup, or compromised admin account into an instant leak of every user's password. Build the safe equivalent instead (a reset-to-a-new-password action) if a similar request comes up again.
16. **Combining `Count()`/`Sum()` annotations over two different reverse relations on one queryset causes row fan-out and silently wrong numbers**, not an error — Django JOINs both relations and multiplies rows together. Every per-user metric on the Users/Ledger pages was rewritten as an independent correlated subquery specifically because of this, and reverified against known test data with exact expected numbers. Use the subquery pattern (`Subquery(Model.objects.filter(...).order_by().values('group_field').annotate(x=...).values('x')[:1])`) the moment a second relation is involved, not a direct annotate.
17. **Django's ORM does NOT use the currently-`activate()`-d timezone when converting a naive datetime for query filtering — it uses the static `settings.TIME_ZONE`.** Template *display* of a datetime *does* respect the active timezone (verified separately) — the two behave differently, which is exactly what makes this easy to get wrong without noticing. Any code that builds a filter value from a naive datetime and needs it interpreted in a specific timezone (e.g. the admin panel's Pakistan-time date filters) must call `timezone.make_aware(naive_dt, that_timezone)` explicitly — see `apps/web/views.py:_parse_pkt_date_bound`.
18. **When two parties settle money between each other at a negotiated/matched price (the exchange's back/lay fills), keep "how much was reserved/released" and "how much money actually moves" as two separately-computed things, even though they're related.** Reserve/release using each side's own originally-requested terms (so the bookkeeping always nets to exactly zero, no drift, regardless of what price a match actually executed at); compute the real profit/loss using the actual executed terms (fair to both parties, especially when one side got a better price than they asked for - "price improvement"). Conflating the two either lets `reserved_balance` drift over time or shortchanges/overcharges a matched party. See `apps/exchange/services.py:_exposure_rate()` / `_settle_fill()` and the dedicated test proving this (`test_price_improvement_backer_gets_better_price`).
19. **For anything this size or riskier, use a formal plan-and-approval step before writing code** — don't just start building. The betting exchange (Section 4.11) went through `EnterPlanMode`/`ExitPlanMode` with the client approving the exact design (data model, matching algorithm, settlement math, commission handling, phase boundaries) before any file was touched. This caught the matching-model question (house-as-counterparty vs. true peer-to-peer) and the commission question early, as design decisions, rather than as rework after guessing wrong.
20. **Two related but distinct correctness traps found while building cash-out (`apps/exchange/services.py`), both caught by writing tests with real hand-computed numbers before trusting the code, not by reading the code and assuming it was right:**
    - **Never let a "target" calculation overshoot when walking an order book level-by-level.** Cash-out works by placing an opposing order sized so its `Σ(stake×odds)` exactly equals a target notional, which is what makes the resulting position's gross profit/loss identical no matter which way the match goes. Taking a whole extra price level once the target is already exceeded seems harmless ("the user just gets a slightly better deal") but it is **not** — it directly breaks the equal-P&L guarantee, producing a real, potentially large imbalance between the two outcomes (proven arithmetically and reproduced in a failing test before the fix — see `_simulate_cash_out_walk`). The fix: take full levels only while still short of the target, then take the *exact fraction* of the final level needed to land precisely on it (an exact division, not a heuristic); Django's existing partial-fill matching (`min(unmatched, resting.unmatched)`) then naturally consumes that exact fraction with no special-casing needed.
    - **Even after fixing the above, a *full* cash-out's value is "estimated," never "guaranteed."** This project charges commission per-fill, on whichever individual bet happens to win — not on a user's net profit across a whole match (which is what real Betfair does). A cash-out deliberately creates two separate fills (the original bet and the new opposing one) that are *gross*-balanced by construction, but if those two fills have different sizes (true whenever the market moved between placing the bet and cashing out — the normal case), commission gets deducted from a different-sized number depending on which fill ends up "the winner," so the two real outcomes differ by `commission_rate × (new_leg_stake − original_fill_profit)` — small when the price barely moved, but genuinely non-zero in general. Rearchitecting commission to be charged on a user's *net* result per match (true Betfair behavior) was considered and explicitly rejected for now — it would require changing the already-proven, already-tested Phase 1 settlement code (`_settle_fill`) that every other bet on the platform depends on, for a benefit (razor-exact cash-out figures) not worth that risk. The wording downgrade ("estimated" everywhere a cash-out value is shown) is the chosen fix, confirmed with the client.
21. **When a new feature needs its own "settings that can change later," snapshot the effective rules onto each individual record at the moment it's created — never have a record compute its own numbers on the fly from a live, currently-editable settings row.** The loss-cashback system (`apps/cashback`, Section 4.12) does this: every `CashbackCredit` freezes the rate, multiplier, and deduct-on-unlock flag that applied at credit time, so an admin changing the global rate next week can never retroactively alter what a user already earned or is already partway through wagering. The same principle already existed for `ExchangeFill.commission_amount` (Section 4.11) — this is now the second time it's applied, confirming it as a general pattern for this project: any time "the rules might change later" and "an existing record must not be affected" are both true, snapshot, don't reference.
22. **Declined: giving one specific user different odds/payout terms than everyone else, silently.** Requested as part of the client's large 2026-09-07 direction (an admin tool to adjust odds "for a specific user"). A *global* or *per-match* odds-margin adjustment (raising or lowering the house edge for everyone) is normal bookmaker risk management and is fine to build. Secretly giving one particular person worse terms than what's shown to everyone else is a different thing — it deceives that specific user about the actual terms of their own bet, which most gambling regulators treat as fraud against a player, not risk management. Declined for the same class of reason plaintext-password storage was declined earlier in this project (Section 8): a request that's understandable in intent but carries real legal/ethical risk gets a clear "here's what I will build instead," not silent compliance or silent refusal.
23. **Verify a third-party API against its *live* behavior, not its docs page, before designing anything on top of it — a docs page can simply be wrong.** While researching ParlayAPI (Section 4.14) as a new odds provider, its own docs page claimed no cricket coverage and didn't mention Betfair one way or the other; direct calls to the live API with the actual key proved cricket sport keys exist, and separately proved Betfair isn't a data source on the API in any form at all (checked its full bookmaker list, not just one endpoint). Both facts changed the actual design. The same session also found two more things no amount of reading would have surfaced: a real, previously-unnoticed bug in the existing odds-outcome-matching logic (matching literal words "home"/"away" instead of the event's actual team names — would have silently produced zero usable matches the moment the real provider was ever turned on, since `apps/sports` had no test coverage before this) fixed in both the old and new provider classes; and a Cloudflare 403 caused by Python's default `urllib` User-Agent string, unrelated to authentication, fixed with a normal-looking `User-Agent` header. None of these four things were visible from documentation or from reading the code alone.
24. **A time-based safety feature (a "delay before X" requirement) needs its underlying goal implemented, not necessarily a literal block/sleep — check what the deployment can actually afford before picking the implementation.** The client asked for a 5-7 second bet-acceptance delay (Section 4.15), which real bookmakers use to stop a user exploiting odds they know are stale. A literal `time.sleep()` in the view would hold a Gunicorn worker thread for that whole window; this project's production config runs only 3 workers (`Dockerfile.prod`), so a handful of concurrent bettors could exhaust the pool and take the whole site down for the sake of one feature. Built instead as odds re-validation at confirmation time (reject if the price moved beyond a small tolerance since it was shown) — same underlying protection, no thread held hostage. Always check what a proposed implementation actually costs the running deployment, not just whether it satisfies the literal words of the request.
25. **When a client describes a specific architecture (WebSocket, in this case) but the codebase has none of the supporting infrastructure and no production deployment to test it against, surface the trade-off and let them choose, rather than either silently building the bigger thing or silently substituting something simpler.** For Section 4.15, the client had already researched and described a hybrid WebSocket/REST design in real technical detail — building a simpler polling-based version instead without asking would have quietly overridden a choice they'd clearly already thought about, even though polling delivers the identical user-facing behavior (same refresh cadence, same viewer-gating, same credit efficiency) with none of the new deployment risk. Asked directly instead, with the actual trade-off named (WebSocket only wins on last-mile latency/overhead at real scale, not on data freshness or provider credit usage) — the client chose polling. Same principle as rule 22, applied to an architecture choice instead of a policy one: when a request implies a specific technical approach, check whether that approach's prerequisites actually exist before assuming it's the only way to deliver what the client actually wants.
26. **Never build, wire in, or extend a mechanism whose actual purpose is to hide a real user's location/identity from a third-party service's own access control — even when it's framed as a performance fix, even under real time/money pressure, and even if another AI assistant already built it into the codebase.** During the casino integration (Section 4.23), a game provider (WM Casino, via SoftAPI) turned out to geo-block Pakistan — the platform's actual target market. The client repeatedly asked for a proxy to route around this (directly, then reframed as "just for our own site," then as "the client supplies the code," then as an already-half-built `casino_proxy/` service another AI session had wired into the project's own files under a "fixes lag" docstring). Declined every version, for the same underlying reason regardless of packaging: it deceives a provider's own access control about where a real user actually is, which risks the client's whole vendor account being terminated for a Terms-of-service violation and adds real legal exposure on top of an already-unresolved question in `client tasks.md` (legal jurisdiction/licensing for real-money gambling). The framing changing (technical justification, "who writes the code," "our own infrastructure") does not change what the mechanism does — decline all of them, consistently, and say so plainly rather than re-litigating each rephrasing from scratch. The actual, legitimate fix for a provider that can't serve the client's market is a different provider (as happened here — Waija replaced SoftAPI as the active provider once confirmed to have no such block), not disguising the ones who can't.
